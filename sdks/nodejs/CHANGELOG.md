# Changelog

## 2.5.0 — 2026-10

- **Agent memory.** Six new nodes let an agent keep notes between conversations in a folder of markdown (`MEMORY.md`, `memory/<topic>.md`, `people/<id>.md`): **Memory** reads the index, the current person's notes and the names of the other files into a block for a System Prompt's `{{MEMORY}}` (with editable `guidance`), and **List / Read / Write / Edit / Delete Memory** are plugin tools the model works it with. The store is the host's: `config.memory.path` (a folder), `config.memory.instance` (any `MemoryStoreInterface`: SQL rows, bucket objects), or an in-process default. Paths are validated and file sizes capped in front of every store. A shared memory can keep a private page per person (`config.memory.people: true` plus `person: { id, name }`): the agent sees and changes only the page of whoever is talking, and a `person.id` that can't be a file name is refused when the engine is created. A store can hold changes for approval (`held`, `pending()`). An imported sub-agent never inherits its caller's memory; `config.memory.forImport(importId)` gives it its own, and an import with memory nodes gets an in-process memory even when its caller has none. The Python SDK has the same nodes, store classes and `config["memory"]` (`for_import` there). New exports `MemoryStoreInterface`, `FolderMemoryStore`, `InMemoryMemoryStore`, `normalizeMemoryPath`. Covered by `tests/test.agent-memory.js`.

## 2.4.0 — 2026-09

- **New `decision` node category for System One models.** OpenRouter now serves a `decisions` output modality: models that take a `state` (text, object, or array) plus a map of typed `questions` and return typed `answers`, instead of chat completions. Question types are `noul` (probability a yes/no statement holds), `choice` (one option from a set, with per-option probabilities and confidence), and `score` (position on 2-10 ordered levels, with probabilities and confidence). The first generation covers TypeSafe Jev (`typesafe-jev-latest`, `typesafe-jev-1-13`), Upstage Solar Decide, Respan Span-01 / Span-01 Lite, and Kev 4B. Each node outputs `answers`, a `values` shortcut map (question id to primary value), the versioned `model` that answered, `usage`, and cost. New integration method `openrouter.systemOne()` / `system_one()` calls OpenRouter's `/systemone` endpoint. The `state` input is typed `string or object or array or array of objects or array of strings or conversation or message`, so chat conversations and messages connect directly; `questions` is a bare `object` because it must be one specific shape. Respan nodes carry `supported_question_types: ["noul"]` because that provider rejects other question types, and they convert a workbench conversation into Respan's required `{ input, output }` span with string content (a conversation must end with an assistant reply). Generated by the new `scripts/generate_decision_nodes.js`. Covered by new flow tests `flow.decision-jev-typed-answers.json` (all three question types), `flow.decision-conversation-state.json` (one conversation fed to Jev, Solar Decide, Kev and Span-01), and `flow.jev-router-chat.json`.
- **Router models generate as chat nodes.** Router models such as `typesafe/jev-router` pick an underlying model per request, and OpenRouter lists them with pricing of `-1` and no supported parameters. The LLM generator previously would have produced a completion-style `prompt` node with a negative baked price. Routers are now detected, generated as chat nodes, and marked with `pricing.variable: true`; per-request cost comes from OpenRouter's reported usage. A new `model_overrides` block in `generator.config.json` declares the parameters a router accepts (verified live for Jev Router: tools, tool_choice, temperature, max_tokens). When baked pricing has no usable rates, cost is now split between input and output lines by token count rather than attributed entirely to input.
- **`:batch` model variants are skipped by all generators.** OpenRouter added `:batch` variants of many models that only work through its asynchronous batch API; the synchronous endpoints reject them with a 404, so generated nodes would always fail.
- **Model catalog refresh.** Regenerated LLM, embedding, rerank, and decision nodes from OpenRouter. Models no longer listed are tombstoned (kept and marked deprecated) rather than deleted.
- **Python SDK imports again.** The `zv1` to `Workbench` rename left five error subclasses and two sub-flow call sites referencing the removed `Zv1Error` / `Zv1` names, so `import src` failed. They now use `WorkbenchError` / `Workbench`, and `Zv1` / `Zv1Error` remain as legacy aliases.

## 2.3.0 — 2026-08

- **Provider-agnostic inference config.** The primary LLM endpoint is now configured with `keys.inference` + `inferenceBaseURL` instead of the OpenRouter-branded `keys.openrouter` + `openrouterBaseURL` — so pointing the engine at your own OpenAI-compatible endpoint (vLLM/Ollama/TGI/LiteLLM) no longer means setting something called "openrouter". The old names remain accepted as backward-compatible aliases, and the default endpoint is still OpenRouter. A custom base URL now also selects the plain OpenAI dialect automatically (drops OpenRouter-only payload fields), so self-hosted endpoints receive clean OpenAI-shaped requests; an explicit `openrouter.ai` base URL keeps full usage accounting. Covered by `tests/test.custom-inference.js`.
- **Bring-your-own inference endpoints.** A host can register custom OpenAI-compatible or Azure OpenAI endpoints and route flow nodes to them instead of the platform OpenRouter endpoint. `Workbench.create(flow, { customInferenceProviders: { <name>: { baseURL, apiKey, dialect: "openai" | "azure", apiVersion?, models? } } })` builds a `custom:<name>` integration per provider, reusing the OpenRouter integration's completion logic with a configurable destination + dialect (`azure` uses `AzureOpenAI` — deployment-as-model + `api-version`). OpenRouter-only payload fields (`provider`, `usage:{include}`) are omitted for custom dialects so strict servers don't reject them. New node **`custom-inference`** resolves `settings.provider` → the `custom:<provider>` integration and sends `settings.model`; the host rewrites its own `byo:<provider>:<model>` nodes to this at run time. Covered by `tests/test.custom-inference.js` (dialect construction, payload trimming, end-to-end flow routing).

## 2.2.0 — 2026-08

- **Template variables holding structured data now render as JSON instead of `[object Object]`.** `system-prompt`, `message`, and `string-template` coerced every variable with `String()`/`str()`, so connecting a nested object or an array to a `{{key}}` / `{key}` placeholder injected `[object Object]` (or `[object Object],[object Object]` for a list) straight into the prompt. Non-string values are now JSON-encoded with 2-space indent; strings still pass through untouched. This also closes a JS/Python divergence — Python's `str()` emitted `True`/`None` where JS emitted `true`/`null`; both now go through JSON encoding, and null/`None` renders as an empty string rather than the literal word. Covered by new `system-prompt.tests.json` and `message.tests.json`, plus four new `string-template` cases.
- **`object` inputs that hold opaque data accept `array of objects` connections.** The editor rejects a connection when the source's declared type isn't in the target input's `type` string, so an "Array of objects" output could not feed `json-to-yaml` even though its serializer already handled arrays. Widened to `"object or array of objects"`: `json-to-yaml.json`, `json-to-xml.json`, `object-merge.objects`, and the `variables` inputs on `system-prompt`, `message`, and `string-template`. Inputs that need one specific shape are deliberately unchanged (LLM `response_format`, `response-format.schema`, `tool.parameters`, `http-request.headers`/`query`, the object-property accessors, and third-party payloads/filters).
- **Array-of-objects arriving on a single connection is flattened rather than swallowed.** `object-merge` and the three `variables` inputs treated a connected array as one opaque entry, so its objects were silently dropped from the merge or never matched a `{{key}}` lookup. All four now flatten one level. Fixed in the JS and Python engines.

## 2.1.3 — 2026-08

- **MCP tool arguments named `name` are no longer clobbered.** Tool identity and tool arguments were merged into one flat object: the engine call site spread the model's arguments and set `name` to the tool name (overwriting any argument called `name`), then `callMCPTool` destructured `name` back off as the tool name (stripping it from the forwarded arguments). Tools with a top-level `name` parameter received `name: undefined` and failed server-side validation with `-32602`. `callMCPTool` / `call_mcp_tool` now take `{ name, arguments }` as distinct fields end-to-end, and arguments are forwarded verbatim; unexpected top-level keys throw, so a legacy flat-shape caller fails loudly instead of silently dropping arguments. JS + Python engines updated in lockstep. Covered by `tests/test.mcp-name-arg.js`.
- **New node `prompt-injection-guard`** — heuristic prompt-injection detection for conversations, per the OWASP LLM Prompt Injection Prevention Cheat Sheet: instruction overrides, jailbreak personas, system-prompt extraction, safety-bypass requests, template-marker spoofing, typoglycemia-scrambled variants (bounded Damerau-Levenshtein), and base64-smuggled payloads. Flagged messages are replaced with a neutral third-person withholding note — an earlier instructional notice was itself read as an injection attempt by the model. Stateless, offline, JS + Python parity, 13 shared test cases.
- **Tool-call node events carry `toolName` and `toolCallId`.** `onNodeStart` / `onNodeComplete` / `onNodeError` around tool dispatch previously carried only `nodeId` + `nodeType` — the integration node shared by every tool on an MCP server — so a live-trace UI could not label a per-tool chip or pair start with completion across a multi-round loop. Purely additive; existing fields unchanged. Applied to all four emit sites, including the invalid-JSON-args error branch. Covered by `tests/test.tool-call-events.js`.
- **Idle watchdog: `config.idleTimeoutMs` bounds time-without-progress.** The flow timeout is a wall-clock cap on the whole run, so a multi-round agent doing many quick tool calls eats the budget while never actually stalling. `idleTimeoutMs` (opt-in) aborts only after N ms without progress — every node-execution boundary, tool dispatch and settle, and streaming token delta stamps activity, and sub-engine activity chains upward so a parent awaiting a hard-working sub-agent is not idle. Same abort path as the wall cap. Covered by `tests/test.idle-timeout.js`.

## 2.1.2 — 2026-07

- **Image-bearing tool results reach the model as vision inputs.** MCP tool results carrying image content blocks were `JSON.stringify`'d into the text-only `role:"tool"` message — the model received base64 as text and confabulated the image's contents. Image blocks are now delivered as an ephemeral `image_url` user message placed above the entire trailing tool-cycle run on the wire (so multi-round tool cycles all survive into the `conversation` output), while the `role:"tool"` message carries a short text note in place of the raw bytes — identical on the wire, in multi-round history, and in the final output. Fixed in the JS and Python engines. Covered live by `tests/flows/flow.chat-tool-image.zv1` (the model must actually identify the image; full cycle preserved; no vision message leaks) and deterministically by `tests/test.tool-vision.js` (wire shape + multi-round cycle survival, no network).

## 2.1.1 — 2026-07

- **Assistant text alongside tool calls is no longer dropped.** The tool loop rebuilt the assistant turn as `{ role, content: null, tool_calls }`, discarding any narration the model emitted before calling its tools (e.g. "Let me search for that!"). The text was lost from both the final `conversation` output — even though it had already streamed to the user — and from the model's own context on subsequent rounds, compounding across turns in chat flows. Fixed in the JS and Python engines; covered by `tests/test.tool-loop-content.js`.

## 2.1.0 — 2026-07

- **`search-internet` is backed by Firecrawl Search.** Google's Custom Search JSON API is closed to new customers, so the macro now wraps a new `firecrawl-search` node (`POST /v2/search`) and requires a `firecrawl` key instead of `google_custom_search`. The macro's surface is unchanged: `query` in, `results` out — an array of `{ title, link, displayLink, snippet }` (each item also carries `position`). Default result count is 5 (was 10).
- New vendor node `firecrawl-search`: `query` + `limit` (default 5, clamped 1–100) in; `items` / `total_results` / `warning` out. `FirecrawlIntegration` gains a matching `search()` method (JS + Python).
- `google-custom-search` is unchanged for existing keys, but its backing API is unprocurable for new customers.

## 2.0.0 — 2026-07

First stable release of `@zerowidth/workbench-sdk` (successor to the `zv1` package — drop-in: same `Workbench` API).

### Knowledge bases
- Full knowledge-node family: `semantic-search`, `keyword-search`, `query-knowledge-base`, `describe-tables`, `list-documents`, `read-chunks`, `expand-chunk-context`, `get-chunk-by-index`, `combine-document-chunks` — plus graph traversal: `list-entities`, `get-entity-neighbors`, `find-entity-path`.
- Per-node knowledge bases: a `knowledge-base` node binds a specific KB to specific search nodes (`flow.knowledgeDbPaths`, keyed by uuid), alongside the flow-global KB.
- **Bring your own knowledge base**: pass any object implementing the exported `KnowledgeBaseInterface` via `config.knowledgeBase.instance` (flow-global) or `config.knowledgeBase.instances[kbUuid]` — run flows against your own SQL database, vector store, or service. The interface now declares every method knowledge nodes call.

### Fixes
- **Nested imports (import-within-import) resolve for the first time.** A spread-order bug in the `.zv1` loader clobbered each import's loaded nested-definitions array with the raw `{id: snapshot}` request map, so second-level imports silently never registered (empty outputs pre-2.0; unknown-node-type error under the new loud validation). Caught by the new `flow.nested-imports.zv1` test.
- **Unknown node types now fail at load.** `Workbench.create` throws `Flow references unknown node type(s): …` when a flow names a node type that isn't in the catalog (removed model, typo, missing import). Previously the node silently never executed and the flow "completed" with empty outputs.
- **Imported subflows are callable as LLM tools again.** The `zv1 → Workbench` class rename left a stale reference in the import-to-node-type converter, so every imported-flow tool call failed at runtime with `Workbench is not defined`. Covered by the new `flow.chat-tool-chain.zv1` test (two dependent sequential tool calls).
- **`disconnect()` no longer deletes database files by path heuristic.** File lifecycle belongs to the creator: the engine cleans its own temp extractions; hosts opt in to cleanup of paths they provide with `config.knowledgeBase.cleanupDbFiles: true`. (Previously, a path merely containing `knowledge_` or `.temp` was unlinked after every run.)
- `query()` routes only true `LIMIT 1` statements to single-row mode — `LIMIT 10`/`LIMIT 100` return full result sets.
- Host-injected knowledge-base instances are never clobbered by file-path registrations; per-uuid registration runs regardless of a global instance.
- Python `query-knowledge-base` node gains the per-uuid resolver and 1000-row result cap matching the JS variant.

### Also
- `keyword-search`, `list-documents`, and `read-chunks` are callable as LLM tools (`is_plugin`).
- `node:sqlite` + loadable `sqlite-vec` — no native module builds.
